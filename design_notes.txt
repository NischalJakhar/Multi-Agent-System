Munder Difflin Multi-Agent System — Design Notes / Reflection
================================================================

1. Architecture
----------------
The system uses 4 agents (within the 5-agent limit), built with smolagents.
See workflow_diagram.svg for the visual version of what's described below.

- orchestrator_agent (CodeAgent): the only agent the "customer" talks to. It
  never touches the database directly (it has zero tools of its own) — its
  entire job is to delegate to the three worker agents, decide what can be
  fulfilled, and compose the final customer-facing reply.

- inventory_agent (ToolCallingAgent): checks stock and delivery feasibility.
    check_item_stock       -> get_stock_level()
    check_full_inventory    -> get_all_inventory()
    estimate_delivery_date  -> get_supplier_delivery_date()

- quoting_agent (ToolCallingAgent): prices requests.
    get_item_catalog   -> paper_supplies (catalog lookup, for name matching)
    get_quote_history  -> search_quote_history() (rationale/reference only)
    quote_line_item    -> catalog unit price + tiered bulk discount

- ordering_agent (ToolCallingAgent): commits money-affecting actions.
    check_cash_balance    -> get_cash_balance()
    get_financial_report  -> generate_financial_report()
    place_stock_order     -> create_transaction() [stock_orders]
    finalize_sale         -> create_transaction() [sales]

Decisions behind this split:
- The three worker roles map 1:1 onto the three business operations the
  project asks for (inventory checks, quoting, order fulfillment), so
  responsibilities don't overlap and each agent's tool list stays small and
  auditable.
- Pricing and charging are made deterministic on purpose: quote_line_item and
  finalize_sale both compute price from the real catalog unit price and a
  fixed discount schedule (0% under 100 units, 5% at 100+, 10% at 500+, 15%
  at 1000+) rather than trusting a number the LLM types out. This guarantees
  the amount quoted to the customer always matches the amount charged, even
  though the model's own prose about the price is not always reliable (see
  below).
- finalize_sale and place_stock_order resolve item_name case/whitespace
  -insensitively against the catalog (_resolve_item_name) so trivial
  formatting differences ("A4 Paper" vs "A4 paper") can't silently create an
  untracked, mismatched inventory line.

2. Evaluation (test_results.csv)
----------------------------------
All 20 requests in quote_requests_sample.csv were run in chronological order,
tracking cash and inventory value before/after each. This is the fourth full
run (the first three surfaced bugs, below, that were fixed in between).
Starting point (as of 2025-04-01, after seed stock purchases): cash
$45,059.70, inventory $4,940.30. Ending point (2025-04-17): cash $45,535.68,
inventory $4,423.20 (both sane and positive — no negative stock anywhere).

Against the rubric's evaluation criteria, going strictly by the transaction
ledger (not the response text — see finding (f) below for why that
distinction matters here):
- Cash balance changed on 3 of the 20 requests (requests 4, 6, 7 — meets,
  but does not comfortably clear, the 3-required minimum).
- Those same 3 requests are the only ones with a real, ledger-backed sale
  (>= the 3 required, but only just).
- 17 of the 20 responses explicitly state a reason for a line item that
  could not be fulfilled (out of stock, no catalog match, insufficient
  stock for the requested delivery date), confirming not every request is
  approved.

Strengths observed:
- The system correctly and clearly declines items that are genuinely out of
  stock or don't exist in the catalog, and says why, in plain language,
  often citing the real stock number (e.g. "only 122 sheets available").
- Deterministic pricing means every quoted discount is arithmetically
  correct and reproducible, independent of the LLM's own (sometimes
  garbled) restatement of the numbers.
- No negative stock and no sales of items unrelated to the actual request
  anywhere in this run's ledger (see (b) and (c) below — both confirmed
  fixed by this run).
- No quote/charge mismatches: unlike an earlier run, quoting_agent and
  ordering_agent no longer independently guess different substitute items
  for the same ambiguous request (see (c2) below — confirmed fixed).

Limitations found by auditing the transaction ledger against the raw request
text (not just the chat transcript — this is the main lesson from this
evaluation: the ledger, not the model's narration, is the actual source of
truth):

a) Timeout-triggered duplicate transactions (run 1 only). smolagents'
   CodeAgent has a default 30-second timeout per reasoning step. A step that
   delegates to several managed agents (each a real LLM call) can exceed
   that easily; the killed step was retried from scratch, re-running
   finalize_sale/place_stock_order calls that had already committed,
   duplicating several sales. Fixed by raising the timeout
   (executor_kwargs={"timeout_seconds": 300}). Confirmed fixed: zero
   timeout events in this run.

b) No hard guard against overselling (run 1 & 2). Nothing originally
   stopped finalize_sale from selling more units than were actually in
   stock; by the end of run 2, several items had gone negative (e.g. A4
   paper at -11,128 units), driving the final inventory value negative.
   Fixed by adding a check inside finalize_sale that raises if the
   requested quantity exceeds actual stock as of the sale date. Confirmed
   fixed: no item has negative net stock in this run.

c) Item-name substitution on ambiguous requests (run 1 & 2). Name
   resolution is exact (case/whitespace-insensitive) match only. When a
   customer's wording didn't correspond to any single catalog SKU (e.g. "A4
   glossy paper", where the catalog has separate "A4 paper" and "Glossy
   paper" entries but no combined one), the ordering agent sometimes gave up
   trying to match the requested item and instead sold a completely
   unrelated catalog item (e.g. "Invitation cards") just to have something
   to report as fulfilled. Fixed by explicitly instructing the orchestrator
   and ordering_agent to treat an unmatched name exactly like insufficient
   stock (decline and explain) and never substitute a different item.
   Confirmed fixed: every sold item in this run traces back to an actual
   request.

c2) Quote/charge mismatch from independent re-guessing (run 3). Even after
   (c) was fixed, quoting_agent and ordering_agent were each independently
   free to interpret an ambiguous item description, and could land on two
   different catalog items for the same request: in one case quoting_agent
   quoted "A4 glossy paper" as "Glossy paper" ($38.00) while ordering_agent
   separately charged it as "A4 paper" ($9.50) — the customer was quoted
   one price and actually charged a different one, for a different item.
   Fixed by making inventory_agent the sole item-name resolver: it now
   states each item as "RESOLVED: <description> -> <canonical item_name>"
   or "UNMATCHED: <description>", and the orchestrator is instructed to
   pass that exact canonical name to both quoting_agent and ordering_agent
   rather than letting them each re-interpret the customer's wording.
   Confirmed fixed in this run: no quote/charge mismatches found.

d) Partial-batch retries duplicate already-completed sales (minor, still
   present). When one request lists several items and some of them fail to
   match the catalog, the ordering_agent can retry a whole batch instead of
   just the failed items, re-selling an item that already succeeded. This
   run showed a much smaller instance of it (a duplicated 1-unit, $0.20
   restock) than earlier runs (previously a 10,000-unit sale duplicated 3x).
   Not yet fixed; see suggestion #2 below.

e) Rationale isn't always faithful to the actual system state. The system
   has, across runs, invented plausible-sounding but false reasons not
   backed by any tool call — e.g. declining an order citing "insufficient
   cash balance" when the real balance was healthy. Root cause traced (see
   (f)) to ordering_agent occasionally using a hallucinated date (e.g.
   "2023-10-03" instead of the real request date) for check_cash_balance,
   producing a false $0.00 reading — and then stating that internal cash
   figure to the customer, despite explicit instructions never to reveal
   cash balance externally. Not fully code-fixable: date parameters are
   legitimately dynamic per request, so there's no catalog-style ground
   truth to validate them against the way item names can be (see
   suggestion #3).

f) Fabricated "fulfilled" claims with zero backing transaction (found in
   this run, fixed after it completed). In 5 of the 20 requests (1, 3, 5,
   16, 17), the orchestrator's customer-facing text stated specific items
   were "Fulfilled" at a stated price — but ordering_agent was never even
   invoked for that request, so no finalize_sale transaction exists in the
   ledger at all (cash_balance/inventory_value are unchanged from baseline
   for those rows in test_results.csv). This is more serious than (c2):
   it's not a wrong-item charge, it's a complete fabrication of a
   successful transaction. Root cause: the orchestrator, once it had a
   price from quoting_agent, sometimes composed a "success" response
   without ever completing step 4 (delegating to ordering_agent). Fixed
   after this run by requiring the orchestrator to only state an item is
   fulfilled if ordering_agent's response for that exact item, in that run,
   included a real transaction_id — otherwise it must report the item as
   not fulfilled. Smoke-tested (not re-validated at full scale): the exact
   scenario from request 1 above now correctly reports non-fulfillment
   instead of fabricating success — though that same smoke test is what
   surfaced the cash-balance date hallucination described in (e). Per a
   deliberate choice not to spend another full ~30-minute run chasing
   further hallucinations, this fix is included in project_starter.py but
   test_results.csv above still reflects the pre-fix (fabricating) behavior
   for requests 1, 3, 5, 16, and 17 — treat those five rows' "fulfilled"
   claims as unreliable; the other 15 rows are consistent with the ledger.

Overall assessment: guardrails that are enforceable in code (catalog name
resolution, price computation, stock checks, the transaction-id-required
rule) have all been verified to hold. Guardrails that depend entirely on
the LLM (gpt-4o-mini here) correctly following a written instruction —
using the right date, not inventing a rationale, always completing a
multi-step delegation — were reduced in severity across four rounds of
fixes, but not eliminated, and probably can't be through prompting alone.
That's a property of using a smaller model as the decision layer, not a
bug in any single instruction.

3. Suggestions for further improvement
-----------------------------------------
1. Fuzzy/semantic item matching. Replace exact-match catalog resolution with
   similarity-based matching (e.g. token overlap or embedding similarity)
   so descriptive requests like "A4 glossy paper" resolve to the closest
   real SKU(s) with a confidence score, and fall back to an explicit decline
   only below some threshold — instead of either an exact-match failure or a
   fabricated substitute.

2. Idempotent transactions. Give create_transaction an idempotency key
   (e.g. hash of item + type + date + request_id) so that any retried agent
   step — whether from a timeout, a network error, or the ordering_agent
   retrying a whole batch after one item in it failed to match (finding d
   above) — can never double-book the same logical sale or restock. This
   would also let the ordering_agent be told "just retry, it's safe" instead
   of needing per-item retry logic.

3. Validate the customer-facing rationale against tool outputs before
   sending it. Add a lightweight check (rule-based or a second LLM pass)
   that confirms every claim in the final response (price, reason for
   non-fulfillment, delivery date) is actually backed by a tool result from
   this run, to catch cases like the invented "insufficient cash balance"
   rationale, or the fabricated-fulfillment cases in finding (f), before
   they reach the customer.

4. Use a stronger model for the orchestrator. Several remaining issues
   (date hallucination, skipping a delegation step while still claiming
   success) are instruction-following failures rather than logic bugs.
   Swapping MODEL_ID from gpt-4o-mini to a stronger model would likely
   reduce their frequency, at higher per-request cost.
